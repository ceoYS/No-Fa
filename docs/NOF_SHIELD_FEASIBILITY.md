# NoF Shield — 기술 타당성 검토 (Feasibility)

> Status: **검토 문서 (no implementation)**. 작성 2026-06-01.
> 이 문서는 "NoF 실드(콘텐츠 차단)"가 플랫폼별로 **지금 가능한 것 / 아직 불가능한 것 /
> 위험한 것**을 정리한다. 이번 라운드에서는 **OS 레벨 차단을 구현하지 않는다.** 제품
> 아키텍처와 UI 플레이스홀더만 만든다.
> 함께 보기: [NOF_SHIELD_PRODUCT_SPEC.md](./NOF_SHIELD_PRODUCT_SPEC.md) ·
> [NOF_SHIELD_ROADMAP.md](./NOF_SHIELD_ROADMAP.md)

## 0. 한 줄 요약 (TL;DR)

- **앱 안(in-app)에서 시스템 전체를 차단하는 것은 불가능하다.** iOS/Android 모두 일반
  앱이 다른 앱이나 사파리/크롬의 트래픽을 임의로 막을 권한을 주지 않는다.
- **가장 빨리, 정직하게 차단을 제공할 수 있는 길은 PC 브라우저 확장과 NoF 자체 안전
  브라우저다 (P1).** 둘 다 "우리가 그리는 화면 안에서" 동작하므로 OS 권한 다툼이 없다.
- **기기 전체 차단(P2)은 가능하지만 비싸다.** iOS는 Screen Time/FamilyControls +
  Network Extension, Android는 VPNService 기반 로컬 DNS 필터가 필요하다. 둘 다
  앱 심사·프라이버시 리스크가 크다.
- **SNS 인앱 이미지 모자이크(P3)는 현재 신뢰성 있게 불가능하다.** 연구만 한다.

---

## 1. 무엇을 막으려 하는가 (Scope of "blocking")

| # | 차단 대상 | 설명 | 난이도 |
|---|-----------|------|--------|
| B1 | 성인 사이트·도메인 | 알려진 도메인/URL 접근을 막음 | 중 |
| B2 | 자극적인 검색어 | 검색 키워드를 가로채 흐리거나 경고 | 중상 |
| B3 | 앱·SNS 위험 줄이기 | 자극으로 빠지기 쉬운 앱/피드 진입을 늦춤 | 상 |
| B4 | SNS 피드 이미지 모자이크 | 노출 이미지를 실시간으로 흐리게 | 매우 상 (P3 연구) |

핵심은 **B1·B2를 정직하게 먼저** 제공하고, B3·B4는 "되는 척"하지 않는 것이다.

## 2. 플랫폼별 타당성

### 2.1 Chrome 확장 (Chrome Extension) — **P1, 가장 현실적**

- **가능성: 높음.** Manifest V3 `declarativeNetRequest`로 도메인/URL 차단(B1),
  콘텐츠 스크립트로 검색 결과·키워드 처리(B2)가 가능하다.
- **장점**: OS 권한 다툼 없음. 차단 룰을 로컬에 두면 방문 기록을 서버로 보낼 필요가
  없다(프라이버시 우위). 배포가 빠르고 업데이트가 쉽다.
- **한계**: 데스크톱 크롬/엣지 한정. 모바일 사파리·크롬에는 적용 안 됨. 사용자가
  확장을 끄거나 시크릿 모드로 우회할 수 있다 → "마찰을 늘리는" 도구이지 "완벽한 벽"이
  아님을 제품 카피에서 정직하게 말해야 한다.
- **심사 리스크**: 낮음~중. Chrome Web Store 정책 준수 필요(권한 최소화, 데이터 사용
  고지).

### 2.2 NoF 안전 브라우저 (NoF Safe Browser) — **P1, 모바일의 첫 답**

- **가능성: 높음.** iOS `WKWebView` / Android `WebView`를 감싼 자체 브라우저를 만들면,
  **우리 브라우저 안에서는** URL 화이트/블랙리스트(B1)와 검색어 가로채기(B2)를 완전히
  통제할 수 있다.
- **장점**: 앱 심사 통과가 비교적 쉽다(시스템을 건드리지 않음). 모바일에서 "안전하게
  검색/탐색하는 공간"을 제공.
- **한계**: 사용자가 기본 사파리/크롬을 쓰면 우회된다. 즉 **시스템 전역 차단이 아니라
  "안전한 방 하나"를 제공**하는 모델. 이 한계를 제품에서 숨기면 안 된다.
- **심사 리스크**: 중. 자체 브라우저는 콘텐츠 정책·연령 등급을 명확히 해야 한다.

### 2.3 iOS Safari Content Blocker (확장) — **P2 초입**

- **가능성: 중.** `Content Blocker` 앱 확장은 사파리에 **선언적 룰(JSON)** 을 제공해
  도메인/URL 패턴을 차단(B1)할 수 있다.
- **장점**: 사파리 전역에 적용(자체 브라우저보다 넓다). 룰이 선언적이라 NoF가 사용자의
  방문 내용을 볼 수 없다(프라이버시 우위).
- **한계**: **검색어 단위(B2)의 동적 처리에는 약하다** — 콘텐츠 블로커는 네트워크
  룰/요소 숨김 위주라 "검색 키워드를 흐리는" 정교한 로직은 제한적. 룰 개수 상한도 있다.
- **심사 리스크**: 중. 콘텐츠 블로커 자체는 흔하지만, 성인차단 카테고리는 심사가
  보수적일 수 있다.

### 2.4 iOS Screen Time / FamilyControls + DeviceActivity — **P2, 가장 강력하지만 가장 비쌈**

- **가능성: 가능하지만 제약 큼.** `FamilyControls`, `ManagedSettings`,
  `DeviceActivity` 프레임워크로 앱 사용 제한·웹 콘텐츠 필터(성인 콘텐츠 자동 제한)를
  적용(B1·B3)할 수 있다.
- **장점**: 기기 전역. 앱 실행 제한까지 가능(B3에 가장 근접).
- **한계**:
  - **특별 엔타이틀먼트(Family Controls capability)가 필요**하고 Apple 승인이 까다롭다
    (원래 보호자/자녀 통제용). 본인-자기통제(self-restriction) 용도는 승인 사례가 늘고
    있으나 보장되지 않는다.
  - 사용자가 Screen Time 암호를 알고 있으면 스스로 해제 가능 → "마찰" 모델.
  - 구현·심사 비용이 매우 높다.
- **심사 리스크**: 높음. 엔타이틀먼트 거절 가능성 자체가 리스크.

### 2.5 Android VPN/DNS 로컬 필터 (VPNService) — **P2, 안드로이드의 전역 답**

- **가능성: 높음(기술적으로).** `VpnService`로 **로컬 VPN**을 띄워 DNS/패킷을 가로채
  도메인 차단(B1)을 기기 전역에 적용할 수 있다. 외부 서버로 트래픽을 보내지 않고
  로컬에서 DNS 응답만 거르는 "no-root local DNS filter" 패턴이 표준이다.
- **장점**: 루트 불필요. 모든 앱·브라우저에 적용(B1·일부 B3).
- **한계**:
  - 한 번에 하나의 VPN만 활성화 가능 → 사용자가 다른 VPN을 쓰면 충돌.
  - 키워드 단위(B2) HTTPS 내용 검사는 **TLS 때문에 불가/비권장**(중간자 가로채기는
    프라이버시·보안상 금지). 도메인 레벨까지가 정직한 한계.
  - 배터리·안정성 관리 부담.
- **심사 리스크**: 중상. Google Play는 `VpnService`·접근성 권한 사용을 엄격히 본다.
  용도(자기통제 콘텐츠 필터)를 명확히 고지해야 한다.

### 2.6 SNS 인앱 이미지 모자이크 — **P3, 연구만**

- **가능성: 현재 신뢰 불가.** 타사 SNS 앱(인스타/트위터 등) 화면을 NoF가 가로채
  이미지를 흐리게 하는 것은:
  - iOS: 불가능(다른 앱 화면 접근 권한 없음).
  - Android: 접근성/오버레이 권한 남용에 가까워 Play 정책 위반 위험이 크다.
  - NoF 안전 브라우저 *안*에서 웹 SNS를 볼 때는 온디바이스 비전 모델로 **시도**는
    가능하나, 오탐/누락이 많아 "가려졌다"고 약속할 수 없다.
- **결론**: P3에서 **온디바이스 분류 정확도·지연·배터리만 연구**한다. 제품에 "모자이크
  된다"고 절대 표기하지 않는다.

## 4. 프라이버시 원칙 (비협상)

1. **온디바이스 우선.** 차단 룰 매칭과 필터링은 기기 안에서 끝낸다. 사용자가 무엇을
   검색·방문했는지 서버로 보내지 않는 것을 기본값으로 한다.
2. **로그 최소화.** "막은 횟수" 같은 집계조차 기본은 로컬. 동기화는 옵트인.
3. **TLS 내용 검사 금지.** HTTPS 본문을 까보는 방식(MITM)은 채택하지 않는다.
   도메인/요청 레벨까지가 정직한 한계.
4. **해제는 쉽게.** 자기통제 도구이지 감시 도구가 아니다. 잠금은 "마찰"이지 "감금"이
   아니다(샤임 카피 금지).

## 5. 앱 심사 리스크 정리

- **Apple**: 콘텐츠 블로커는 통상 OK. FamilyControls 엔타이틀먼트는 **거절 가능성**이
  실질 리스크. 성인 콘텐츠 차단 앱은 "왜, 어떻게, 데이터 어디로"를 명확히.
- **Google**: `VpnService`·접근성 권한은 "프라이버시 침해 우려" 1순위 심사 대상.
  용도 명시·데모 영상·정책 페이지가 필요.
- **공통**: NoF 본체(현재 프로토타입)는 차단 기능이 없으므로 지금 심사 영향 없음.
  차단은 별도 컴포넌트(확장/안전브라우저/네이티브 모듈)로 분리해 본체 리스크와 격리한다.

## 6. 결론 — 지금 정직하게 할 수 있는 것

- **지금(P0):** 차단 엔진 없음. 제품 아키텍처 + "준비 중" UI 플레이스홀더만. 가짜
  토글·가짜 차단 카피 금지.
- **다음(P1):** Chrome 확장 **또는** NoF 안전 브라우저로 **URL/검색어 차단을 실제로**
  내놓는다. 범위 한계("완벽한 벽 아님, 마찰 도구")를 카피에 명시.
- **그 다음(P2):** iOS(Content Blocker → Screen Time), Android(VPN/DNS) 네이티브
  전역 차단. 심사·프라이버시 비용을 감수할 가치가 검증된 뒤.
- **연구(P3):** SNS 이미지 모자이크는 정확도 검증 전까지 제품에 노출하지 않는다.
